# CivitasOne Universal Service Designer — UX/UI Design Specification
**Date:** 2026-08-07 · **Status:** build-executable companion to `CIVITASONE-UNIVERSAL-SERVICE-DESIGNER-BRD` (FN-01–FN-33)
**Purpose:** the BRD says *what* each screen must do; this document says *what it looks like, how it behaves, and what quality bar it must meet*. An executor (Claude Code) implementing any FN must satisfy both documents. Where they conflict, the BRD wins on function, this spec wins on presentation and interaction.
**Grounding:** the design-token and component inventory in §3 was verified against `apps/web/src/app/civitas-ds.css` (355 lines) and `apps/web/src/app/_components/ds/` (24 components) on 2026-08-07.
---
## 1. Design Principles (non-negotiable, cited in reviews)
**P1 — Guided by default, expert by choice.** The primary user is a municipal/departmental officer with domain expertise and no technical training. Every block opens in a guided mode with plain-language steps and pre-filled defaults; "Advanced" is a deliberate, labeled door (e.g. the BPMN canvas), never the landing view. If a screen requires understanding JSON, BPMN, regex, or an API to complete, it fails review.
**P2 — Never a blank page.** Every creation flow starts from something: a Service Pattern template, a Domain Pack draft, a cloned existing service, or sensible defaults. Blank-canvas-with-toolbar is a failure mode for this audience. (This is the UX mirror of the BRD's "defaults-first" onboarding rule.)
**P3 — Preview is always one glance away.** The designer must never wonder "what will the citizen see?" Form builder, certificate editor, notification editor, and fee builder all keep a live citizen-view preview visible or one click away, rendered by the *same runtime component* the citizen will use (FN-13) — never a lookalike.
**P4 — Plain language, bilingual-ready.** UI copy uses the vocabulary of government offices, not software: "Approval chain," not "workflow definition"; "Who checks this step?", not "assignee designation"; "Fee," not "demand config." Every Designer-authored string is a per-locale value from day one (FN-18) even while the Designer chrome itself ships English-first.
**P5 — Forgiving.** Autosave everything, always undoable, never lose work. No action inside a draft is destructive; the only irreversible acts are Publish (which is versioned, so even that is recoverable by superseding) and Delete-draft (which requires typed confirmation).
**P6 — Honest states.** Every screen designs its empty, loading, saving, error, and partial states explicitly. No silent failures, no fake optimistic rows (the 2026-08-05 UAT report documented exactly this anti-pattern in DataExportClient — a fake row appearing after a 404'd create; it is banned), no `<pre>JSON</pre>` anywhere in the Designer or runtime. An error message always has three parts: what happened, why (best known), what to do next.
**P7 — One system.** Every screen composes tokens and components from §3. No inline hex colors, no ad-hoc table markup (the current `citizen/catalogue/page.tsx` hand-rolled `<table style=…>` pattern is replaced by `DataTable`), no new one-off components where a system component exists.

## 2. Users & Modes
| User | Mode | Consequence in UI |
|---|---|---|
| Service Designer (dept. functional lead) | Guided wizard (default) | 8-block stepper, plain language, templates, inline help (`HelpTip`) |
| Power designer / implementation partner | Expert surfaces | BPMN canvas, formula editor, raw slab tables — reachable via labeled "Advanced" affordances that warn on entry and round-trip cleanly back to guided mode |
| Department Head (checker) | Review mode | Read-only diff-centric view of a submitted pack; Approve/Reject with mandatory comment on reject |
| Citizen / Company | Runtime (FN-13) | Mobile-first application flow, §7 |
| Counter/CSC operator | Runtime, assisted | Same runtime with dense layout option + `assistedBy` attribution banner |
| Auditor | History mode | Version timeline, read-only everything |

## 3. Design System
### 3.1 Existing foundation (verified — reuse, do not rebuild)
Tokens (`civitas-ds.css`): primary green `--primary:#0e9f6e` (+`--primary-d`, `--primary-soft`), accents (`--indigo --violet --amber --rose --sky --cyan`), neutrals (`--bg:#f4f6f8`, `--panel:#fff`, `--ink:#101828`, `--ink2:#475467`, `--mut:#667085`, `--line/--line2`), full semantic sets for good/warn/bad/info (fg+bg+border each), radii `--r:14px`/`--r-sm:10px`, three shadow levels. **This palette is adequate — the Designer introduces no new colors.** Status mapping is fixed: draft=neutral, in-review=info, published=good, rejected/error=bad, needs-attention=warn.
Components (`_components/ds/`, all with tests): `AppShell, TopBar, Sidebar, PageHeader, Card, DataTable, Tabs, Segmented, StatusPill, StatGrid/StatCard, ProgressBar, ConfirmDialog, Toast, EmptyState, ErrorState, FileUpload, HelpTip, Avatar, ActionButton, Term, ConfidenceBar…` — a real kit. The Designer builds *on* it.
### 3.2 New components required (build once, in `_components/ds/designer/`)
| Component | Used by | Spec summary |
|---|---|---|
| `WizardShell` | FN-33 | Two-column: left block rail (§5.2), main canvas. Sticky footer bar: autosave status ("Saved just now"), Back/Next, Run Test, Submit. |
| `BlockRail` | FN-33 | Vertical list of B1–B8 with per-block status dot (empty / in-progress / complete / error-count badge), click-to-jump, keyboard navigable. Blocks hidden by the Service Pattern render struck-through with a "not used by this pattern" tooltip. |
| `SplitPreview` | FN-02, 04, 07, 08 | Right-hand live preview pane, collapsible, device toggle (mobile 360px / desktop), renders via the real runtime renderer. Refresh ≤300ms after edit (debounced). |

| `ConditionBuilder` | FN-02 (visibility), FN-03 | Sentence-style rows: "IF ⟨attribute ▾⟩ ⟨operator ▾⟩ ⟨value⟩ → ⟨effect ▾⟩", AND-joined, reorderable. No free-text expression entry in guided mode. |

| `TestRunPanel` | FN-10 | Vertical checklist of pipeline steps (form → eligibility → workflow lanes → demand → payment → GL → certificate), each pending/running/pass/fail, fail rows expand to the three-part error + deep-link to the offending block; artifacts (rendered certificate PDF, computed demand lines) shown inline. |

| `StatutoryWarningDialog` | FN-09, 29 | Import-time modal listing statutory references + authority scope, requires explicit acknowledgment checkbox before Import (Platform Admin only for cross-tenant). |
| `StatusTimeline` | Runtime | Citizen-facing vertical progress: done/current/upcoming steps with dates, SLA countdown chip on current step. |

## 4. Information Architecture & Routes
```
/designer                       → Library home (my services, drafts, pack library, domain packs)
/designer/new                   → Pattern picker (modal-route)
/designer/[id]                  → WizardShell, opens at first incomplete block
/designer/[id]/b1 … /b8        → block screens (deep-linkable; BlockRail = same order)
/designer/[id]/test             → TestRunPanel
/designer/[id]/review           → checker review mode (VersionDiff + Approve/Reject)
/designer/library               → pack + domain-pack browse/import
```
The Designer lives in the existing `AppShell` chrome (TopBar/Sidebar) as a top-level module named **"Service Designer."** The legacy read-only `citizen/catalogue` page becomes a redirect to `/designer` for authorized authors and remains the read-only catalogue for everyone else.

## 5. Screen Specifications
### 5.1 Library home (`/designer`)
Layout: `PageHeader` ("Service Designer" + primary button **"New Service"**) → `StatGrid` (Drafts, In Review, Published, Needs Attention) → `Tabs` (My Services · All Department Services · Pack Library · Domain Packs) → `DataTable` (columns: Service, Pattern, Owning Office, Version, Status `StatusPill`, Updated, row actions: Open / Duplicate / History). Empty state (`EmptyState`): "No services yet. Start from a template — most offices begin with a Domain Pack." + two buttons (Browse Domain Packs / New Service). Search-as-you-filter on name/key. **No pagination under 200 rows; virtualize beyond.**
### 5.2 New Service — Pattern picker (`/designer/new`)
Modal with four large selectable cards (Certificate/Permission · Booking · Collection · Grievance), each: icon, one-line plain description, 3 real examples, "what you'll configure" mini-list of its active blocks. Below: "or start from a pack" link → Library tab. Selecting a card → inline name + owning-office fields (office pre-filled from the user's own office) → Create → lands in `/designer/[id]/b1`. Pattern is changeable later from B1 with a confirm dialog listing which block data would be hidden (not deleted — P5).
### 5.3 Wizard shell (all `/designer/[id]/*`)
`WizardShell` + `BlockRail`. Header: service name (inline-editable), pattern chip, version chip, `StatusPill`. Footer: autosave indicator (states: Saving… / Saved just now / Offline — retrying), Back/Next, **Run Test** (enabled when all active blocks ≥ minimally complete), **Submit for Approval** (enabled only after latest Test passed — FN-10 rule, tooltip explains when disabled). Right edge: collapsible `HelpTip`-driven context help per block, written in P4 language.
### 5.4 B1 — Catalogue & Identity
Single-column form on `Card`: name (per-locale tabs), service key (auto-slug, editable once, locked after first publish with explanation tooltip), owning office (org-hierarchy tree-select), offering offices (multi-select, default "all under owner"), channels (checkbox row: Portal · Mobile · Counter/CSC · WhatsApp · API), SLA days (number + "counted from submission" helper), statutory references (repeatable rows: act name + section + link; visible warning banner if pattern=Certificate and list empty: "Certificates usually cite the empowering act — required before cross-tenant sharing").
### 5.5 B2 — Form Builder (deepest spec — the make-or-break screen)
**Layout: three panes.** Left — field palette: grouped registry (Text, Number, Date, Yes/No, Choice single/multi, File upload, Address, Ward/Zone, Applicant-profile fields), each a card with icon + name; click **or** drag to add. Center — form canvas: sections as collapsible groups; fields as rows (`SortableList`) showing label, type icon, required-star, conditional-eye icon if visibility rules exist; selected row highlighted. Right — `PropertyPanel` for the selected field: Label (locale tabs) · Help text · Required toggle · type-specific options (choice list editor with reorder; number min/max; date range; file types+max size) · Validation (pattern presets: PAN, Aadhaar-last-4, mobile, email, PIN — **presets, not regex entry**; regex exists only under Advanced) · Visibility (`ConditionBuilder`: "Show this field IF ⟨field⟩ ⟨op⟩ ⟨value⟩").
**Preview:** `SplitPreview` toggled by a persistent "Preview" button — replaces the palette pane when open (three panes max at any time). Renders the actual runtime form; interactable (designer can type into it to feel validation).
**Interactions:** autosave 2s debounce per change; undo/redo (⌘Z/⌘⇧Z, 50-step stack, survives pane switches within the block); duplicate field; delete field → row-level undo toast ("Field deleted — Undo", 8s), not a confirm dialog (P5: forgiving beats interrogating). Address/Ward fields show a live "bound to: ⟨ULB ward list⟩" chip — binding to `location-service` hierarchy is automatic and visible, never a free-text choice list.
**Acceptance for this screen (beyond BRD FN-02):** a first-time user given only the on-screen copy builds the Trade License form (12 fields, 2 uploads, 1 conditional) in under 20 minutes with zero documentation; every action reachable without a mouse; preview parity with runtime is pixel-exact because it *is* the runtime component.
### 5.6 B3 — Eligibility
`ConditionBuilder` list ("Applicants must meet…"), each row: attribute (grouped picker: profile · form answers) / operator / value / effect (Block · Warn · Flag for review) with per-effect message (locale tabs). "Test against a sample applicant" inline panel: fill sample values → see pass/fail per rule with the failing rule highlighted. Empty state: "No conditions — everyone may apply. That's fine for most services." (skippable per BRD — do not nag).
### 5.7 B4 — Workflow (Approval chain)
**Guided (default):** the pattern's lane template as horizontal `Card` chain: Submitted → [Inspection] → Decision → [Payment] → Issued. Each lane card: step name (editable), **"Who acts?"** designation-select from `tenant-service/positions`, SLA days, optional checklist ref (B6 documents verified here), toggles per template (add/remove optional Inspection lane, add parallel branch from a curated list). A live sentence beneath the chain narrates it: "An application will be inspected by *Licensing Inspector* within *7 days*, then decided by *Licensing Officer* within *5 days*…" — the plain-language readback is the guided mode's verification tool.
**Advanced:** "Open visual editor" button → existing BPMN canvas (`DesignerCanvas`) with a banner: "Advanced editor — changes here switch this service to custom-workflow mode." Round-trip: template mode regenerates BPMN; custom mode disables template controls with an explanatory note and a "Revert to template" (confirm + diff).
### 5.8 B5 — Fee & Revenue
Step 1 — model chooser, three cards (mirrors BRD `feeModel`): **Fixed fee** ("one amount, optional exemptions") / **Slab or formula** ("depends on area, units, category…") / **Engine** ("computed by an assessment engine — you set parameters only"; card disabled with honest message if the bound engine is absent, per Engine Binding rule). Step 2 per model: Fixed → amount (₹, paise-safe input), exemption rows (`ConditionBuilder` + percent/absolute reduction); Slab → `SlabTableEditor` (+ `FormulaInput` under Advanced); Engine → parameter form generated from the binding's config schema. Step 3 — always: **Head of Account** (searchable `finance-service/hoa` select, **required to Submit** — blocking rule surfaced right here, not at publish time), demand trigger state (radio: On submission / On approval), penalty & rebate windows where applicable. Persistent right rail: "Sample calculation" — sample inputs → computed lines shown exactly as demand lines (base / rebate / penalty / total), matching the Demand shape the BRD canonicalizes.
### 5.9 B6 — Documents
`SortableList` of document rows: name (locale tabs), formats (chip multi-select: PDF/JPG/PNG), max size, Mandatory toggle, "Verified at" lane-select (from B4's lanes). Inline preview chip shows how the upload card will look to the citizen. Warning (not block) if a mandatory doc has no verifying lane.
### 5.10 B7 — Output & Issuance
Tabs: **Certificate** (`TemplateCanvas` + `MergeFieldPicker`; output-type select: Certificate / Licence / Closure note / Receipt — Grievance patterns default to Closure note), **Numbering** (`NumberingFormatBuilder`), **Signatory** (designation-select + digital-signature toggle), **Validity** (fixed date / duration / none + renewal linkage note when FN-15 enabled). "Generate sample PDF" button renders via the real issuance pipeline into the preview pane.
### 5.11 B8 — Notifications
`NotificationMatrix`. Default templates pre-seeded per pattern (P2) so the matrix is never empty — designer edits rather than authors. Template editor: locale tabs, merge pills, live character/segment count for SMS, WhatsApp preview bubble styling for that channel.
### 5.12 Test (`/designer/[id]/test`)
`TestRunPanel` as specified in §3.2. Header states the rule plainly: "A service must pass this test before it can be submitted." History of prior runs (`DataTable`, last 10) with pass/fail and duration. Fail rows deep-link into the exact block+field at fault.
### 5.13 Review & Publish (`/designer/[id]/review` — checker only)
Read-only render of every block **plus** `VersionDiff` against the currently published version (or "first version" banner). Sticky decision bar: Approve & Publish (confirm dialog restates service name, version, fee summary, HOA) / Reject (mandatory comment). Maker≠checker enforced server-side; the UI additionally hides the decision bar from the submitter with an explanatory note.
### 5.14 Pack Library & Import (`/designer/library`)
`PackCard` grid, filter rail (sector, pattern, jurisdiction, source). Import flow: Preview (read-only wizard walkthrough of the pack) → `StatutoryWarningDialog` when refs present → "Imported as draft — nothing is live until your office publishes it" success toast → opens the draft.

## 6. Citizen / Company Runtime (FN-13) — UX spec
Mobile-first (360px baseline), thumb-reach primary actions, one section per screen on mobile. Flow: service page (name, plain description, fee "from ₹X", documents needed as a checklist, SLA promise, Apply CTA) → stepped form (section stepper, inline validation on blur, `FileUpload` with camera capture on mobile) → review screen (all answers, edit links per section) → fee screen (demand lines itemized, pay methods) → submitted screen (application number BIG and copyable, expected date, tracking link). Tracking: `StatusTimeline` + notification history. Certificate: download + QR + verify link. Drafts autosave to `application_drafts` (exists in schema) — returning applicants resume with a "Continue where you left off" banner. Counter mode: same flow, dense desktop layout, `assistedBy` attribution bar. Every string bilingual (tenant primary + English) via the locale values authored in the Designer.

## 7. States, Errors, Motion
**Loading:** skeletons (existing shimmer patterns), never spinners-on-white for primary surfaces; block rail renders immediately with cached statuses. **Saving:** footer indicator only — no toasts for routine autosave; toast only on recovery ("Reconnected — all changes saved"). **Errors:** `ErrorState` component with the three-part message (P6); field-level errors inline + summarized at submit; server 4xx map to human copy (a lookup table ships with the build — raw messages never surface). **Empty:** every list/table/matrix has a designed `EmptyState` with one next-step action. **Motion:** 150–200ms ease-out on pane transitions and rail status changes; no motion on data updates inside tables; respect `prefers-reduced-motion`.
## 8. Accessibility & Bilingual (WCAG 2.1 AA + GIGW)
Keyboard-complete (every drag has button parity — §3.2 `SortableList`); visible focus ring (2px `--info`-derived) everywhere; 44×44px minimum targets on runtime, 32px in dense Designer tables; contrast — verify `--mut:#667085` on `--bg` for small text and darken where it fails AA; labels programmatically bound (no placeholder-as-label, anywhere); locale tabs pattern for every authored string with per-locale completeness meter on the wizard footer; Devanagari-safe font stack + `lang` attributes per string for screen readers; certificate PDFs tagged for accessibility.
## 9. Performance Budgets
Preview refresh ≤300ms after last keystroke (debounced); block navigation ≤200ms perceived (prefetch adjacent blocks); form-builder canvas interactive at 100+ fields (virtualize field list beyond 50); runtime first-load ≤200KB JS gzipped on the citizen path (the applicant may be on a 3G Android phone — this budget is a hard gate); autosave payloads are per-block deltas, not whole-pack writes (cache-bust discipline).
## 10. Quality Bar — per-screen review checklist (Claude Code must self-verify)
Before any Designer/runtime screen is "done": (1) zero raw JSON visible; (2) all five states designed and reachable (empty/loading/error/saving/populated); (3) keyboard-only walkthrough completes the screen's primary task; (4) preview parity — citizen-facing previews use the runtime renderer, not a copy; (5) every string passes the P4 vocabulary review (no BPMN/schema/API words in guided mode); (6) tokens/components only — grep for hex literals and inline `<table` in new code must return zero; (7) the screen's BRD acceptance criterion demonstrably passes; (8) screenshot at 360px and 1440px attached to the PR/change description.
